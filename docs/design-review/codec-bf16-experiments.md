# Codec BF16：官方参考与真实负载验证

**本文保留 BF16 实验历史。当前正式实现保留固定 BF16，并新增默认 FP32 路径；状态和验收见 [FP32 优化](codec-fp32-optimization.md)。**
下文零差异结果属于此前长度对齐版本，当前固定计算版本的差异见文末，
FP32 小测见 [对照记录](codec-fp32-check.md)。

2026-09-29。本轮以**未修改官方 tokenizer 的 BF16 单条原长推理**为主要准确度参考，
以真实 selection 任务持续运行时的吞吐为速度验收标准。之前 FP16 C 参考的差异率不能与本文直接比较。
所有实验代码、输入身份、输出与报告位于 `artifacts/codec-padding-review/bf16/`，没有发布 unified features。
生产入口仍是已退役的 legacy C 实现；实验 BF16 不等于生产已迁移。

## 参考和样本

官方参考用固定本地权重调用 `Qwen3TTSTokenizer.from_pretrained(..., dtype=torch.bfloat16)`，
不导入本地 Encoder、不安装 C 补丁，每次 public `encode(wave, sr=24000)` 只传一条实际长度波形。
参考和候选共享经过现有 frontend 解码、混声道、重采样后的 24 kHz 波形；这隔离 tokenizer 差异，
不把 frontend 替换为官方其他重采样实现。

样本从 172 扩展到 509 条：496 个真实样本、13 个边界长度样本，覆盖全部 16 个数据集；
新增 337 条真实样本与原样本不重叠。受已有审计证据覆盖所限，并非每个数据集都有相同数量。
总计 1,140,240 个码字。官方 BF16 在 GPU 1/2 两张 A800 上全部码字一致，首 4 条重复也一致。
参考源码、依赖、权重、实际 dtype/attention 和结果见 `official-reference/bf16_native-*`。

## 本轮发现

- BF16 不能只改 encoder dtype：官方的码本缓存按 BF16 归一化，逐级 RVQ 残差也要舍入回 BF16。
  旧 C 的 FP32 码本缓存和 FP32 残差不是这个参考。
- 卷积须保留“累加输出转 BF16，再加 bias”的舍入边界；首层 7 点卷积采用有序 FP32 FMA。
  部分卷积用 32/64 通道分组的归约顺序，可减小与 cuDNN 的差异。
- 官方在当前依赖环境中传入显式 bool 因果 mask，实际走 PyTorch CUTLASS memory-efficient attention，
  **不是 FlashAttention**。已通过 profiler 确认。测试同一内核的变长接口时，6 个诊断样本采用官方线性层后，
  Transformer 浮点输出完全一致；保留固定归约线性层时仍有差异。
- BF16 固定归约 GEMM 与官方 cuBLAS 的少量舍入差异会经后续层、离散量化放大。
  诊断中关闭 cuBLAS BF16 reduced-precision reduction 没有改变官方输出；FP64 也不保证复现官方。
- RVQ 可用 BF16 Tensor Core 点积并保留 FP32 累加/距离、BF16 残差。相比原 FP32 点积版本，
  509 条中有 19 个码字变化，不能宣称完全等价。

| 实验候选 | 相对官方 BF16 的不同码字 | 差异率 |
| --- | ---: | ---: |
| 初始 BF16 对齐 | 178,402 | 15.6460% |
| 卷积归约对齐 | 128,140 | 11.2380% |
| 再用 PyTorch 变长 FlashAttention | 127,737 | 11.2026% |
| 卷积对齐 + Tensor Core RVQ | 128,147 | 11.2386% |
| 再用 CUTLASS 变长 attention | 128,963 | 11.3102% |

这些是**码字一致性**指标，不是音质下降百分比。各阶段差异不能相加，上游误差会影响后续码本决策。
不能因某个单阶段更接近，就推断完整候选必然更接近。完整报告及逐样本、逐码本统计见 `bf16/summary.json`。
Tensor Core RVQ 候选的 509 条样本在 batch 1/7/8 和逆序下码字一致；跨卡候选验证仍需补齐。

## 速度验收：真实持续负载

此前 short64、mixed32、单条 5/120 秒交替测速只作为内核诊断，**不作为满载吞吐验收**。
单卡固定用例中 BF16 候选曾比此前最快 FP16 候选快约 2%–10%，但真实任务首轮出现按尾批大小重复
编译 Triton kernel 的开销，说明这个结论不能直接推广到实际任务。

实际旧生产配置由归档 `launch.json` 核实：每卡 2 worker，每 worker 4 解码线程，task 最大 4096 行。
本轮回放固定版本的 aishell3、csemotions、emilia 真实任务，保留其自然长度分布，复用 `run.run_task`：
读取 selection → 有界预取与解码 → 原调度器组批 → 推理 → feature fingerprint → Lance 写入 → 回读校验。
只把输出路径改到 artifacts；不启动旧生产任务、不引用已删除的 features。

- `full_load.py`：单 worker / 8 解码线程诊断，3 个候选交替顺序、2 轮；冷启动与后续轮次分开。
- `production_worker.py`、`production_load.py`：单卡 2 worker × 4 解码线程，2 轮真实任务，
  对照此前最快 FP16 候选、BF16 候选和旧 canonical FP16；记录端到端吞吐、纯 encode 耗时、批大小、显存和 GPU 利用率。
- `bf16-runtime-bounds/`：批大小从编译常量改为运行时参数的独立候选，尚未验收；固定 7 步边界搜索针对最大 64 条批次。

多卡验证在单卡候选通过后进行，尤其检查 CPU/存储争用、尾批、跨卡重分配和输出一致性。
当前尚未得出“真实满载不降速”或“精度没有进一步优化空间”的结论。


## 验证顺序与已完成的真实任务诊断

用户随后明确：先用小规模可重复测试筛选候选，最后做完整负载验收。
因此已停止尚未完成的双 worker/官方大规模参考队列；保留已经完成的单 worker 诊断，
待数值候选稳定后再重新启动完整验收。停止记录见 `bf16/full-load-queue-deferred.json`。

单 worker 诊断共 10,026 条不重复真实任务样本，约 19.986 小时音频；每个候选跑两轮。
第二轮包含读取、解码、推理、Lance 写入与回读校验的总耗时为：

| 候选 | 总耗时 | 其中 encode | 音频秒 / 墙钟秒 |
| --- | ---: | ---: | ---: |
| 此前最快 FP16 | 62.907 s | 34.691 s | 1,143.74 |
| BF16 external attention | 61.148 s | 32.532 s | 1,176.64 |
| BF16 CUTLASS attention | 61.024 s | 32.521 s | 1,179.03 |

这是单卡单 worker、共享机器上的诊断结果，不代表正式生产并发配置已通过。
首轮部分新尾批耗时约 4 秒，而复用编译结果后不再出现，说明必须单列 JIT 冷启动。
不能从单个首轮 Emilia 任务直接得出两个 attention 实现存在稳定的倍数性能差距；第二轮差距明显缩小。

## 原生计算顺序对齐：小规模筛选，尚未验收

`bf16-shape-gemm/` 按原始单条长度选择计算策略；依据是原生 cuBLAS/cuDNN 的 kernel 和 launch grid，
不是参考码值拟合。原生 BF16 会随长度改变 split-K、累加顺序，部分 GEMM 还会把中间分块舍入到 BF16。
因此只消除外部 padding 并不能自动获得与逐条官方推理相同的结果。
策略表当前依赖 A800、固定 PyTorch/CUDA/cuDNN 环境，不能直接当成跨硬件生产实现。

同一套 509 条样本、1,140,240 个码值，对照未修改的官方 BF16：

| 实验 | 不同码值 | 差异率 | 状态 |
| --- | ---: | ---: | --- |
| 初版 CUTLASS attention BF16 | 128,963 | 11.31% | 早期基线 |
| 按原生策略对齐主要卷积 | 48,952 | 4.29% | 批次耗时增加约 24%–33%，不接受 |
| 卷积分块并行，再单独归约 | 48,499 | 4.25% | 合并同策略的输出 tile 后回收大部分性能 |
| 补齐 `encoder.layers.10.block.1` 的 24,000 个长度策略 | 37,820 | 3.32% | 继续筛选，尚未满载验收 |

分块并行版本 v2 与 v1 的全部 509 条输出相同。补齐残差卷积后的配对小测试中，
短样本 64 条批次耗时增加约 1.1%，混合 32 条批次增加约 2.1%；尚不满足“不降低速度”的结论。
单条延迟不作为最终性能验收指标。

独立输入验证中，Transformer 在 45 条基准样本上与官方逐值相同（包含长度为 1 的特殊分支）；
量化器在 6 条真实样本的相同官方输入上码值相同。这些局部结果不代表全链路精度已达标。
剩余卷积差异和批大小/顺序不变性仍在排查，完整生产并发回放留待候选稳定后执行。
此阶段全部结果保留在 artifacts，未向 unified 写入新 features。

### 后续定位与优化

- 合并 Q/K/V 的 kernel 调用，保留单个投影的 K 维累加策略；相同的 RoPE 只计算一次。
  509 条样本验证这些性能改动没有改变输出。
- Transformer 独立验证扩大到 509 条，相同官方输入下全部逐值相同。
  量化器独立验证中仅 3 条样本、24 个码值不同；全链路差异不能归因于量化器这一项。
- 补齐早期卷积的短形状策略后，全链路差异为 36,181 / 1,140,240（3.17%）。
  另外检查了测试集出现的 601 个较长形状，其原生策略都与既有 group-32 回退一致。
  这仍不代表已覆盖生产中所有可能长度。
- 在最后一层 split-K 卷积中，抽查的 4 条样本只有“最后分块先累加，然后依次加其余分块”
  能全部逐值对齐原生输出。采用该归约后，509 条全链路差异降为 **3,980 个码值（0.349%）**，
  97 条样本仍有差异；跨 GPU、反序、每批 7 条与每批 8 条的结果完全一致。
- 该版配对小测试：短批 64 条耗时约降低 2.2%，混合批 32 条约增加 0.9%。
  还不能以小测试宣告真实满载不退化。剩余高差异短样本指向 `encoder.layers.10.block.3`
  的 1×1 投影，正在检查其 cuBLAS 分块与舍入策略。

证据：`transformer-validation-509.json`、`quantizer-shape-509.json`、
`reduction-order-search.json`、`lastfirst-comparison.json`、`speed-lastfirst-paired.json`，
均位于 `artifacts/codec-padding-review/bf16-shape-gemm/`。

### 量化边界复核候选：509 条零差异，速度仍在筛选

两处残差 1×1 投影按原生 GEMM 策略处理后，全链路只剩 24 个不同码值。
对齐 `cdist` 的范数相加顺序及平方根舍入消除了这 24 个，但另外 2 条样本出现 18 个不同码值。
不能把该变化描述为已经完全复现原生 `cdist`。

候选增加近距离边界检查：若最近两个距离相差不超过 2 个 FP32 ULP，使用原始样本实际长度，
从相关 RVQ 链首次触发的量化层开始调用官方 codebook，更新其后残差。复核必须保持官方的
列主序残差布局；直接给原生 codebook 行主序输入也可能改变其 FP32 归约结果。
此阈值是待扩大验证的经验防护，不是对任意输入严格成立的数值误差上界。

进一步依据本地 PyTorch 2.8 `ATen/native/cuda/Reduce.cuh` 对齐范数归约，
独立随机 BF16 输入测试覆盖 1–1500 帧，范数全部逐值一致；融合到距离选择中，
并缓存固定 codebook 的 FP32 视图，减少重复转换与 kernel 调用。

当前 `guarded_norm` 候选在 509 条 / 1,140,240 个码值上与官方 BF16 **零差异**；
15 条样本触发复核，共调用 116 个原生量化层。跨 GPU、反序、每批 7 条再次对照官方也为零差异。
这只是冻结小测试集的结果；策略表仍绑定当前硬件与依赖，未完成大规模真实任务精度验收。

509 条按现有调度器形成 34 个批次，冷启动与暖态分开计时。当前暖态速度存在几个百分点的回归
与共享环境波动，尚不宣告达到“不降速”。继续尝试融合 Transformer GEMM 的缩放/残差 epilogue，
保留每一步 BF16 舍入，并使用逐批交替的配对测量减少时间漂移影响。
完整并发任务回放仍应在这些筛选通过后执行。

### 完整任务回放已启动

融合 epilogue 后小测试仍为零差异，连续组批的速度差距约为几个百分点，未足以证明实际场景退化
或提升。因此转入用户要求的最终真实场景判断，不能把小测试耗时当作生产吞吐结论。

冻结候选位于 `artifacts/codec-padding-review/bf16-full-validation/candidate/`，
使用 `GuardedNormCandidate`，未采用没有明显测速收益的距离矩阵局部最小值融合分支。
最终快照还修正了最短帧范数的 warp 内累加顺序；宽动态范围的 1–1500 帧独立测试全部一致，
冻结版本 509 条码值复测为零差异。

回放使用 aishell3、csemotions、emilia 的 18,060 条不重复任务样本，单卡双 worker，
每 worker 4 个解码线程。顺序为旧基线、新候选、新候选、旧基线，每阶段跑两轮，
完整保留读取、解码、现有组批、推理、Lance 写入及回读。
运行前由固定 selection 的帧数/采样率枚举新增计算长度，补查 16,912 个原生形状策略；
当前完成的候选阶段没有遇到未覆盖的形状。

冷启动和暖态将分别报告；完整码值验收由另外生成的逐条官方 BF16 参考完成。
在该比较结束前，509 条零差异不能写成 18,060 条零差异，也不能宣告整体任务完成。

### 首次完整结果与消减误差修正

首次完整官方比较：18,060 条 / 26,749,056 个码值中，候选有 9 条样本、131 个不同码值；
四次候选回放彼此完全一致。相比第一次基线的冷启动结果，不能夸大吞吐收益：
后置基线完整阶段为 134.90 s，两次候选阶段为 130.71 s 和 131.36 s，
该组完整吞吐约高 2.7%–3.2%；单轮暖态仍有共享机器波动。

扩样暴露的错误涉及大范数项相减后的距离误差。例如一条样本的两个平方距离约为
429.1914 和 429.1929，而输入与码本范数约为 4,022 和 3,057。
直接按最终平方根距离的 2 ULP 判断接近程度，会漏掉这种消减误差。
逐层复查确认这两条诊断样本的 CNN、Transformer 和投影与原生同输入输出一致，
且官方重复三次的结果稳定，不能把错误归于参考随机性。

第二版快照 `bf16-full-validation/candidate-scaled/` 保留原 ULP 检查，另外在平方距离上使用
`2 * float32_epsilon * (input_norm + embedding_norm)` 的尺度条件触发原生复核。
该条件仍是经验防护，不宣称为任意输入的严格误差界；不依据数据集或样本 ID 分支。
它修正了已发现的全部 9 条 / 131 个差异，原 509 条及跨卡反序回归也为零差异，
小测试触发复核的样本仅从 15 条增至 17 条。

第二版完整精度与吞吐复测写入 `production-load-scaled/`，保留第一版的所有结果供比较。

## 最终实验结果

最终选择 `bf16-full-validation/candidate-scaled/norm_candidate.py` 的 `GuardedNormCandidate`。
实验验收结束时结果仅在 artifacts。用户随后授权全量运行，已将该快照接入
`src/tts_data_pipeline/codec/qwen3_12hz/bf16/`，使用新的生产入口、profile 和运行目录。
旧任务保持退役；正式启动记录见 `docs/codec.md` 与 `reports/codec/active.json`。

| 验证项 | 结果 |
| --- | --- |
| 原 509 条、跨 GPU / 反序 / 每批 7 条回归 | 与官方 BF16 码值零差异 |
| 完整 18,060 条实际任务样本 | 26,749,056 个码值，零差异 |
| 完整任务第二轮重放 | 零差异 |
| 最终双 worker 回放，共 36,120 次样本处理 | 候选 131.292 s，紧邻旧基线 130.862 s |
| 完整端到端音频吞吐 | 候选 2,026.94 音频秒/秒，基线 2,033.61 音频秒/秒 |
| 量化边界原生复核 | 982 / 36,120 次样本处理，约 2.72%，共 6,726 个量化层 |
| 完整任务出现未覆盖计算形状 | 0 |

最终紧邻比较中候选吞吐低约 **0.33%**；此前相同配置的暖态基线完整阶段为 134.896 s，
候选阶段为 130.715–131.361 s，说明共享机器存在几个百分点的波动。
因此准确结论是“这组实际双 worker 负载中吞吐基本持平，覆盖集码值全部对齐”，
而不是稳定提速 3%，也不是统计上证明任意场景绝不退化。

参考为未修改的官方 tokenizer、显式 BF16、逐条实际长度推理，双方使用相同 24 kHz 前端输入；
比较前检查 target ID、输入哈希与输出形状。完整任务涉及 aishell3、csemotions、emilia，
实际时长约 1.003–34.212 秒；另有 509 条跨 16 数据源和边界长度的冻结测试，最长 120 秒。
这是对所覆盖样本和固定 A800 / CUDA 12.6 / PyTorch 2.8 / cuDNN 9.10.2 环境的实验结论，
不构成对所有未来输入、其他软件栈或八卡并发的无限泛化保证。
当前覆盖集已经没有剩余码值差异；后续应用到其他环境需要重新验收。

## 生产接入时的一次性长度核查

全量 selection 为 16 个来源、128,220,178 条，共 436,871 种 24 kHz 输入长度。
对原表未覆盖的四个层补查了 298,717 个层名/输出长度组合：
早期 CNN 三层分别为 121,611、121,611、28,430 个，残差 1×1 投影为 27,065 个。
这里只按元数据枚举长度、运行对应原生层查询算法，并非新增 30 万条完整音频精度测试。
所有新增组合均使用此前默认策略；88 个按算法和长度分布抽取的层输出比较也为零差异。
正式包的 509 条回归与验收快照一致。

按用户要求，这项核查仅保留为一次性验证证据，不作为日后全量启动或新来源接入的强制门槛。
未收录的长长度继续沿用早期卷积 `[32, 1]`（通道组 32、单次归约）和残差投影
`[1, 128, false, 0, false]`（单累加器）的默认策略，不因缺少表项而报错或逐项补查。
不保存与默认值相同的约 30 万个冗余表项，也不累计每个未收录长度的运行记录。
模型自身 120 秒输入范围保持不变；这不是对任意未来输入码值完全一致的保证。
证据位于 `artifacts/codec-production-bf16/`，包括元数据扫描、原生 kernel 策略和逐层对照。


## 计算规则消融与生产代码整理

在同一 509 条 / 1,140,240 个码值上，分别将指定部分的长度规则替换为该算子的
最常见固定策略，其余数值路径和量化复核保持不变：

| 关闭的长度规则 | 不同码值 | 比例 |
| --- | ---: | ---: |
| 全部 | 119,477 | 10.478% |
| 仅卷积 | 117,195 | 10.278% |
| 仅线性层 | 100,387 | 8.804% |
| 仅早期 CNN 和 resproj7 | 3,071 | 0.269% |

这些比例衡量 token 一致性，不是音质差异。最后一项仍保留其他层的长度规则，不能
解释成“去掉所有规则仍只有 0.27%”。真实音频子集 496 条上的全部关闭差异为 10.702%。
原始结果为 `artifacts/codec-production-bf16/ablation-*.json`；小批计时不作满载吞吐结论。

生产代码保留等价数值路径，改用 `PackedModel` 组合卷积、线性层与量化组件，删除
实验类继承链及旧 FP16 实现。BF16 子包仅保留 model、convolution、linear、quantization、
policies 五个实现模块；五个展开的 JSON 表无损压缩为约 5 KB 的 `policies.py`，
14 类运算、77 条区间例外，逐项核对与原表一致。未知长度使用默认策略。
整理后的首次 509 条复测保持零差异。


## 最终取舍：删除长度 policy

用户确认关注计算原理和实现简洁性，接受底层浮点累加顺序导致的码值差异。
已删除 `policies.py`，不保留 77 条长度区间规则，也不做未来形状补查。
卷积使用固定 kernel 配置，线性层统一单累加器；公式、BF16 舍入边界、
样本边界、causal attention、16 码本定义和外部无 padding 语义保持不变。
公式相同不等于浮点逐位结果相同；差异可能通过残差量化传递，不能把 token 差异率当音质损失。

最终源代码在 509 条上的不同码值数及逐码本分布与 `fixed_all` 消融一致：
119,477 / 1,140,240（10.48%）。因此旧长度对齐版本的零差异和全量验收不适用于当前版本。
整理但尚保留规则的中间版本曾在双 worker 实际读写中测得 124.96 s，对照旧候选为
130.32 s；这是中间版本记录，不能替代删除规则后完整吞吐的验证。
该阶段曾暂停全量启动，随后转入 FP32 优化；后续满载验收和运行状态见 FP32 优化专文。
